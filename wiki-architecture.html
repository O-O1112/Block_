Engine Architecture

To truly understand how Block achieves polyglot orchestration without a virtual machine, we need to dive under the hood. Block is built around a high-performance C# Orchestrator.

The C# Orchestrator

At the core of the Block engine is the Orchestrator, written in C# (.NET 8.0). When you execute a .blk script, the Orchestrator performs the following lifecycle:

  1. Lexical Analysis: The .blk file is parsed into an Abstract Syntax Tree (AST). It separates native Block syntax from the embedded polyglot blocks (<py>, <js>).
  2. State Initialization: A localized .state.json file is created in memory (or a secure temp directory) to hold all native variables.
  3. Subprocess Spawning: When the AST evaluator encounters a polyglot block, it spawns a native subprocess (e.g., python.exe or node.exe).
  4. Code Injection & IPC: The Orchestrator dynamically wraps your code with an injection header and footer. The header loads variables from the state file, and the footer writes the mutated variables back to the state file before the subprocess exits.

3-Stage Masking Security

Because Block executes native code and passes variables across process boundaries, security is a top priority. Block employs a 3-Stage Masking system to prevent injection attacks during state serialization:

  • Stage 1 - Regex Validation: Variable names are strictly validated against a regex pattern (^[a-zA-Z_][a-zA-Z0-9_]*$) to ensure they cannot contain execution payloads.
  • Stage 2 - Type Assertion: The Orchestrator enforces strict JSON-type assertions during cross-boundary transit. Only Primitives (Strings, Numbers, Booleans) and basic Arrays/Objects are passed.
  • Stage 3 - Subprocess Isolation: Each polyglot block is executed in an ephemeral, isolated subprocess. Code execution errors immediately kill the subprocess without crashing the Orchestrator.

Performance Considerations

Because Block spawns subprocesses for polyglot blocks, there is a slight overhead compared to native C++ or Rust execution. However, this overhead (typically ~15ms to ~45ms per block) is negligible for most orchestration scripts, CI/CD pipelines, and data-glue applications.
